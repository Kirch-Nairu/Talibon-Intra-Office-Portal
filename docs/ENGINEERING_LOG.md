- Idempotency marking: only routes explicitly carrying `integration.idempotency:<operation>` require `Idempotency-Key`; `GET /api/v1/integration/self` remains non-idempotency-keyed. Foundation B adds only the isolated proof write `POST /api/v1/integration/proof-writes` under authoritative scope `integration.proof.write` and operation `integration.proof.write`.
- Idempotency scope/persistence: `integration_idempotency_records` is uniquely scoped by `integration_client_id + integration_client_credential_id + operation + idempotency_key_hash`. The raw client key is not persisted; only `SHA-256(idempotency key)` is stored. The request fingerprint is SHA-256 over a canonicalized method/payload representation and intentionally excludes Authorization/bearer material.
- Concurrency strategy: a short committed database transaction uses the unique scope constraint plus row locking to create/observe the authoritative `processing` claim. The executing request owns a random processing token. Same scoped key + same fingerprint while processing returns stable `409 integration_idempotency_in_progress`; same scoped key + materially different fingerprint returns stable `409 integration_idempotency_conflict`. Correctness does not rely only on in-memory/cache locking.
- Completion/replay semantics: successful JSON responses persist a safe replay snapshot of status/body with the original correlation ID removed. The business mutation, outbox insert, idempotency completion snapshot and completion audit commit in the same authoritative database transaction. Same key + same fingerprint after completion returns the original logical result without re-running the application/domain action or creating a second outbox record. Replay injects the new HTTP request's correlation ID and marks the response `Idempotency-Replayed: true`; correlation identity is never reused across HTTP requests.
- Failure semantics: non-success/exceptional execution does not falsely persist a completed response. Authoritative action/outbox/completion work rolls back; the claim is then marked `failed` separately with no replay snapshot. A later same-key/same-fingerprint attempt may explicitly reclaim a failed record with a new processing token and incremented attempt count.
- Stable errors/audit: Foundation B adds `integration_idempotency_key_required`, `integration_idempotency_conflict`, and `integration_idempotency_in_progress`. Audit records distinguish original execution start/completion/failure, replay, conflict, rejected concurrent duplicate, and invalid/missing key. Idempotency records and audit summaries do not persist bearer tokens, credential plaintext secrets or Authorization headers.
- Transactional outbox: additive `outbox_messages` stores public event UUID, event type, aggregate type/reference, JSON payload, occurrence/availability times, pending/claimed status, claim owner/time, attempt count and last error. `TransactionalOutbox::record()` refuses to persist outside an active authoritative database transaction, keeping business mutation and outbox creation atomic.
- Dispatcher boundary: `OutboxDispatcher` provides internal claim/release semantics using PostgreSQL row locking with `FOR UPDATE SKIP LOCKED`. It does not perform third-party HTTP calls, external publication, queue delivery or transport. No Kafka, RabbitMQ, microservice split, webhook delivery or published-message claim is introduced.
- Proof surface/schema: additive `2026_08_23_150000_create_integration_idempotency_records_table.php`, `2026_08_23_150100_create_outbox_messages_table.php`, and `2026_08_23_150200_create_integration_proof_writes_table.php`. `integration_proof_writes` is an isolated non-production-domain proof surface used only to verify the idempotency/outbox contract without broadening Correspondence/Documents/Legislative/HR APIs.
